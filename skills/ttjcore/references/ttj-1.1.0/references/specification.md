# TTJ Specification v1.1.0

**Task–Ticket–Job 管理規格**

- [定義] 規格版：`1.1.0`。
- [定義] 文書状態：`stable`。

## 1. 基本原則

- [定義] **TTJ**：担当や環境が変わっても、作業・申し送り・知識を安全に継続する規格。
  - [任意] 単一主体・複数主体の分担・担当引き継ぎ・長寿命 Task の継続運用に使う。
  - [必須] 必要な情報を一度だけ記録する。
  - [必須] **Task / Ticket 分離構造の単一 JSON スキーマと配列・単一オブジェクトの原則**：0〜複数があり得る項目（`workers`, `sessions`, `knowledge`, `tasks`, `tickets`, `jobs`, `runs` 等）のみ配列とし、1つだけに定まっている項目（ルートの `project`、`Task.handoff`、`Run.wait`）は配列にせず単一オブジェクトとする。JSON 文書のルートオブジェクトは `protocol`（`"TTJ/1.1.0"`、必須）・`workers`・`sessions`・`project`・`tickets` の5キーのみで構成し、Project / Task 階層は単一オブジェクト `project` 配下の `project.tasks[]`（および `project.knowledge[]`・`project.tasks[].handoff`。`Task` の中に `tickets` は持たない）、Ticket 以下の作業階層はルート直下の `tickets[].jobs[].runs[]` に分離・統一する。各 `Ticket` は所属する親 Task を `task_id`（`tsk-*`、必須）で参照し、`Ticket.jobs` には ID 文字列配列ではなく `Job` オブジェクトの実体を実行順に格納する（親要素の内側に配置される `Task.project`・`Handoff.task_id` 等の逆参照は持たない）。
  - [必須] **空配列・未記載項目の省略規則とファイル分割**：すべての配列フィールドは、空配列 `[]`・1要素 `[ {...} ]`・複数要素 `[ {...}, {...} ]` のいずれも許容し、空配列 `[]` の場合はそのフィールドの記載自体を省略できる（省略時は空配列 `[]` として扱う）。また、単一オブジェクトの `project` も Ticket 分割ファイル等で記載しない場合は省略できる。これにより、100% 同一のルート JSON スキーマのまま、Task 側の管理ファイル（`protocol` と単一オブジェクト `project` 等のみを記載し `tickets` は省略）と、チケット単位の分割ファイル（`protocol` と `tickets` のみを記載し `project` 等は省略）にファイルを分けてチケット単位で排他操作する運用と、1ファイルにまとめる運用の双方を統一的に扱える。
  - [禁止] 不要な分類・専用の型・重複記入・不要な状態機械を増やす。
  - [禁止] 特定の Agent・Bot・オーケストレーター実装への依存を TTJ へ組み込む。
- [定義] **規格の識別**：`protocol` は JSON 文書の規格名と版を表す。
  - [必須] JSON で保存・交換する場合は文書ルートに `protocol: "TTJ/1.1.0"` を持つ。
  - [定義] 同じ文書に含まれる子レコードはその版を共有し、個別の転記は不要。
  - [必須] 読み手は規格名と版を確認して解釈する。
  - [任意] 識別項目は生成側が補完する。
- [定義] **ラベル**：その行の扱いだけを示し、配下の項目へ継承しない。
  - [定義] **[必須]**：準拠に必要な条件。
  - [定義] **[禁止]**：実施してはならない操作。
  - [定義] **[推奨]**：通常は採用し、外れる場合は理由を残す規則。
  - [定義] **[任意]**：必要な場合だけ選ぶ情報・操作。
  - [定義] **[定義]**：用語や値の意味。
  - [定義] **[例]**：特定の実装や値を強制しない説明例。
  - [必須] 箇条書きの各項目にラベルを付ける。

## 2. 管理単位と作業主体

- [定義] **Worker**：作業の責任を負う主体。
  - [必須] 一意に識別できる不変の `id`（接頭辞 `wkr-`）と、変更可能な表示名 `name` を持つ。
  - [禁止] 人間・Bot・Agent・AI・Service 等の種別分類を業務上の作業主体として区別する。
  - [禁止] `owner_type` や Worker 種別を必須にする、または Worker 種別で Job・Ticket の状態遷移や達成判定を分岐させる。
  - [定義] 認証方法や実行環境ごとの設定は外部環境側で管理し、TTJ に持ち込まない。
- [定義] **Session**：Worker が実際の作業実行を行う単位。
  - [必須] 一意に識別できる `id`（接頭辞 `ssn-`）と、所属する Worker を参照する `worker_id`（`wkr-*`）を持つ。
  - [定義] 同じ Worker が複数の Session を持て、各 Session を個別に識別できる。
  - [禁止] Session の終了・切断・変更によって既存 Ticket の `worker_id` や `session_id` を書き換える。
- [定義] **Project**：作業と長期知識を保持する継続的な領域。
  - [必須] ルートの単一オブジェクト `project` として `id`（接頭辞 `pj-`）と意味の分かる `name` で識別する（任意で `knowledge[]`・`tasks[]` を保持し、Ticket 分割ファイル等で記載しない場合は `project` 自体を省略可）。
  - [例] リポジトリ1つは粒度の目安。
  - [任意] リポジトリなし、または複数リポジトリを含む領域として運用する。
  - [禁止] Task の終了・削除に連動して長期知識を失わせる。
  - [定義] 共通の作業状態や自動完了は規定しない。
- [定義] **Task**：Project 内の長寿命な成果目標を管理する単位。
  - [必須] `project.tasks[]` の要素として配置され、`id`（接頭辞 `tsk-`）・`objective`・`criteria`（および任意の `status`・`deadline`・`resume`・`handoff`）を持つ（`Project.tasks[]` の内側に配置されるため逆参照の `Task.project` フィールドは持たず、`tickets` はルート直下の `tickets[]` に分離されるため `Task` 内には `tickets` や `jobs` を持たない）。
  - [必須] 単一の Project に属し、目標・達成条件・ルート `tickets[]` のうち `task_id` で当該 Task に紐づく複数 Ticket の管理・結果集約・現在の進捗・ブロッカー・揮発性 Handoff（`handoff`）・最終達成判定を扱う。
  - [任意] 期限がある場合だけ `deadline` に Task の完了期限を書く。
  - [必須] 期限を記載する場合はタイムゾーン付きの ISO 8601 日時を使う。
  - [定義] 期限の超過そのものは作業状態の遷移条件にしない。
  - [定義] Task は個々の Ticket のライフサイクルより長く存在できる。
  - [禁止] 修正・再実行・再レビューによる Ticket 増加を理由に新しい Task を作成・増殖させる。
  - [禁止] Ticket の完了数だけで Task の達成率や目標達成を決定する。
- [定義] **Ticket**：単一 Worker の単一 Session が担当する、一方向の作業単位。
  - [必須] ルート直下の `tickets[]` の要素として配置され、`id`（接頭辞 `tkt-`）・`task_id`（所属する親 Task の ID `tsk-*`）・`worker_id`・`session_id`・`objective`・`jobs`（`Job` オブジェクトの配列、空配列時は省略可）を持つ。
  - [必須] `task_id` で単一の親 Task（`tsk-*`）に属し、存在する単一の `Worker.id`（`wkr-*`）を `worker_id` で、その Worker に属する単一の `Session.id`（`ssn-*`）を `session_id` で参照し、`jobs` に `Job` 実体を実行順に格納する（ID 文字列配列による実体分離は行わない）。
  - [任意] その Ticket で「やらないこと（対象外・除外事項）」を `exclusions`（文字列の配列：空配列時は省略可）に明記し、LLM や担当者間の認識すり合わせの精度を上げる（`exclusions` は `Ticket` にのみ配置し、`Job` や他のエンティティには配置しない）。
  - [禁止] 実行時に `Ticket.exclusions` に記載された対象外・除外事項の作業を行う。
  - [定義] Ticket は短命でよく、次 Ticket が未作成でも終了・アーカイブできる。
  - [定義] 終了判定は Job の状態から行い、独自の `criteria` は持たない。
  - [禁止] 会話・Session・接続・Run の終了だけで Ticket を完了にする。
- [定義] **Job**：完了可否を `criteria` で機械的または確認可能な証拠により判断できる最小実行単位。
  - [必須] `tickets[].jobs[]` の要素として配置され、`id`（接頭辞 `job-`）・`objective`・`criteria`（および任意の `instructions`・`status`・`result`・`artifacts`・`resume`・`runs`）を持つ。`runs` は実行試行 `Run` オブジェクトの配列とし、未実行等の空配列時は省略できる。
  - [必須] 単一 Ticket の `jobs` に属し、その位置で順序と親を特定する。
  - [任意] 目標だけでは手順が伝わらない場合だけ `instructions` を補う。
  - [禁止] 親 ID や順序番号を重複記入させる。
  - [禁止] Job に複雑な分岐・処理ロジック、子 Job、個別担当、汎用依存関係グラフ、Handoff 排他制御、待機制御の詳細構造を持たせる。
  - [禁止] `HumanJob`・`BotJob`・`AIJob`・`HumanWaitingJob`・`BotWaitingJob` 等の種別ごとの Job 分類を作る。
- [定義] **目標**：`objective` は Task・Ticket・Job すべてで「何を達成したいか」を表す。
  - [必須] 階層によってフィールドの意味を変えない。
  - [必須] Task・Job の `criteria` には、完了を確認できる条件を1件以上書く。
  - [禁止] 同じ目標・成果物・確認条件を別の欄へ転記させる。
- [定義] **識別**：`id` は保存中のレコードを一意に参照する値。
  - [必須] 重複を避けるため、Project・Task・Ticket・Job・Run・Worker・Session（全7種）の `id` は自動採番とし、それぞれ `pj-`・`tsk-`・`tkt-`・`job-`・`run-`・`wkr-`・`ssn-` の接頭辞（prefix）に続けて `<接頭辞>-<ID（英数字6桁または8桁）>-<インクリメント（ゼロ埋めなしの1始まり整数: 1, 2, 3...）>` 形式（正規表現：`^(pj|tsk|tkt|job|run|wkr|ssn)-[A-Za-z0-9]{6}([A-Za-z0-9]{2})?-[1-9][0-9]*$`）に統一する。
  - [例] Project: `pj-a1b2c3d4-1`、Task: `tsk-e5f6a7b8-1`、Ticket: `tkt-c9d0e1f2-1`（連番: `tkt-c9d0e1f2-2`）、Job: `job-1a2b3c4d-1`（連番: `job-1a2b3c4d-2`）、Run: `run-5e6f7a8b-1`（連番: `run-5e6f7a8b-2`）、Worker: `wkr-7c8d9e0f-1`（連番: `wkr-7c8d9e0f-2`）、Session: `ssn-2b3c4d5e-1`（連番: `ssn-2b3c4d5e-2`）。
  - [必須] Project と Worker は対象を判別できる名称（`name`）を持つ。
  - [任意] 上記7種以外の他レコード（知識・監査記録等）の ID 形式・発行方法・保存先は運用で決める。
  - [禁止] 同じ ID を複数のレコードへ割り当てる、または Project・Task・Ticket・Job・Run・Worker・Session に指定外の ID 形式・接頭辞を使う。
- [定義] **記入形式**：各階層は単一ルートスキーマの中でそれぞれ必要な情報だけを持つ。
  - [必須] 単一オブジェクト `project` 配下の `project.tasks[]`（および `project.knowledge[]`・`project.tasks[].handoff`）とルート直下の `tickets[].jobs[].runs[]`（各 `Ticket` に `task_id` 必須）の分離スキーマに従う（ルートの `project` を配列 `projects` にしたり、`Task` の内側に `tickets` を置いたり、ルート直下に `tasks`・`jobs`・`runs`・`handoff`・`knowledge` を置いたり、`Ticket.jobs` を ID 文字列配列にして実体を外に出したりしない）。
  - [禁止] 共通化のために全階層へ同じ項目を追加する。
  - [定義] フィールドと記入例およびファイル分割時のサンプルは [JSON参照形式](json-format.md) に、代表的な場面ごとの状態遷移とサンプルパターンは [代表ユースケースとサンプルパターン](use-cases.md) に示す。

## 3. 単一 Owner 原則と担当セッションの固定

- [定義] **単一 Owner 原則**：Project および Task の状態の最終確定者を単一 Owner に固定する。
- [定義] **Ticket の担当固定**：`Ticket.worker_id`（`wkr-*`）と `Ticket.session_id`（`ssn-*`）は、その Ticket と配下の全 Job を実行する単一の担当 Worker および担当 Session を表す。
  - [必須] Ticket 作成時に存在する単一の `Worker.id` を `worker_id` に、その Worker の単一の `Session.id` を `session_id` に指定する。
  - [禁止] 1つの Ticket に複数の Worker や複数の Session を設定する。
  - [禁止] Job ごとに独立した担当を設定する。
  - [禁止] 同じ Ticket の担当（`worker_id`・`session_id`）を途中で変更・挿げ替える、または別 Session・別 Worker で同一 Ticket を実行する。
  - [定義] 同じ Worker（および同じ Session）が複数の Ticket を担当することは許可する。
- [必須] **別 Worker・別 Session の作業と再開不可時の引き継ぎ**：別 Worker に独立作業や追加依頼を行う場合、または担当 Session が無応答・再開不可となった場合は、既存 Ticket の持ち主を付け替えるのではなく、新しい Ticket を作成して新しい Session で稼働させる。
  - [必須] 再開不可となった旧 Ticket は停止・安全確認の上で `status: "canceled"`（`cancel_reason` 必須）として閉じ、同一 Task 配下に起票した新規 Ticket の `refs` で旧 Ticket を参照し、必要に応じて `Handoff` で作業文脈を引き継ぐ。
  - [必須] レビュー・調査・承認・操作依頼・依頼先からの追加依頼も通常の Ticket と Job で表現する。
  - [禁止] `Request` を独立した業務オブジェクトとして導入する。
  - [定義] 同じ条件であれば、どの Worker が担当しても状態遷移と達成判定は同一とする。
- [定義] **Worker と Session の分離**：責任主体（Worker）と実行単位（Session）を明確に分ける。
  - [禁止] 同じ Worker に属することを理由に、`Ticket.session_id` と異なる別 Session がその Ticket を無断実行する。
  - [必須] `Ticket.session_id` と一致しない Session からの作業実行・状態更新は、同一 Worker であっても拒否する。
- [定義] **直列性**：同じ Ticket 内で同時に進める Job は最大1つとし、定義順に一方向で進行する。
  - [禁止] 同じ Ticket の別 Job を同時実行する。
  - [禁止] 同じ試行の再送を二重実行する。
- [定義] **v1.0.0 からの廃止事項**：旧 `assignee`、同一 Job の共同作業の仕組み、同一 Ticket の担当交代、Job 内の複雑な試行状態管理、Task 完了後も残る恒久 `Ticket.handoffs` は v1.1.0 で廃止する。

## 4. 固定計画と Ticket 増加への対応

- [必須] **正式作成**：Ticket と全 Job の定義を原子的に確定する。
  - [必須] `Ticket.jobs` に `Job` オブジェクトを実行順に格納する。
  - [必須] Job 列の結果で Ticket の `objective` を達成できることを確認する。
  - [任意] 正式作成前の Draft やテンプレートを編集する。
- [禁止] **確定後の変更**：Ticket 確定後に担当セッション（`worker_id`・`session_id`）、Job 列、および作業定義を変更しない。
  - [禁止] Job の追加・削除・移動・並べ替え、`objective`・`exclusions`・`criteria`・`instructions` の実質変更、完了済み Job への巻き戻し・再入力。
  - [任意] 状態・結果・成果物参照・中止理由・管理記録を更新する。
- [必須] **追加・修正・再実行**：修正・再実行・再レビュー・再開不可時の引き継ぎ・想定外の作業は通常の新 Ticket として同一 Task 配下に作成する。
  - [禁止] 終端 Task へ新 Ticket を追加する。
  - [禁止] 修正・再実行を理由に新しい Task を増殖させる。
  - [推奨] Ticket の Job 数や作業量に上限を設ける。
- [定義] **Ticket 増加への対策**：修正・再実行・再レビュー・引き継ぎによる Ticket 増加を許容しつつ、Worker 種別を問わず起票と管理の負荷を最小化するため、準拠する実装・運用は次の機能を備える。
  - [必須] **Ticket テンプレート**：確定前は編集可能とし、確定後は Job 列を固定する。
  - [必須] **標準 Job 列**：反復する工程を再利用可能な標準定義として提供する。
  - [必須] **後続 Ticket 生成支援**：前 Ticket の成果物・結果・中止理由を引き継いだ新 Ticket 起票を支援する。
  - [必須] **前 Ticket の成果物参照と中止理由参照**：`refs`・`artifacts`・`cancel_reason` により重複作業と文脈断絶を防ぐ。
  - [必須] **Ticket 系列表示と終了 Ticket の折りたたみ**：派生・修正・再実行の系列を追いやすくし、終了済み旧 Ticket をアーカイブ・折りたたんで扱えるようにする。
  - [必須] **Task 単位の進捗集約と現在 Handoff 表示**：Ticket 完了数のみではなく Task の `criteria`・主要成果・ブロッカー・現在 Handoff で状況を提示する。
  - [任意] これらの機能の交換形式・保存構造・具体的な UI 実装方法は利用環境や運用に応じて選択する。
- [必須] **Task の範囲変更**：権限を持つ主体と変更前後・理由を記録する。
  - [禁止] 未達の必須範囲を無記録で除外する。
  - [禁止] 終端 Task の目標・完了条件を変更する。

## 5. 作業状態・結果分離と再開

- [定義] `todo`：対象と配下が未着手。
  - [必須] Task・Ticket・Job の初期値にする。
- [定義] `doing`：対象または配下が着手済みで未終了。
  - [定義] プロセスが現在動いている必要はない。
- [定義] `waiting`：Task・Ticket・Job が現行計画に含まれる外部結果・前提条件の成立を待機している状態。
  - [例] Task 全体の外部承認・計画イベント待ち、前提 Ticket の完了待ち、レビュー・承認結果待ち、外部コマンドや複合スクリプト内の操作結果待ち。
  - [禁止] 待機対象の実装種類や Worker 種別によって状態遷移を分岐させる。
- [定義] `paused`：明示的な判断による保留。
  - [必須] 実行再開には明示解除と、残る待機・障害の解消が必要。
  - [必須] 保留中も未解消の待機・課題を保持し、解除時に再評価する。
- [定義] `blocked`：スクリプト異常・必要な成果物の欠落・実行環境の不備・必要な作業の実施不能・復旧未完了など、現行計画では継続できない計画外の問題がある状態。
- [定義] `completed`：その単位の完了判定を満たした終端状態。
- [定義] `canceled`：権限を持つ主体が中止した終端状態。
- [定義] **status と result の分離**：`status` は進行状態、`result` は確認された作業結果・業務判定を表す。
  - [必須] Job の完了（`status: "completed"`）と業務上の判定結果（`result`：`approved`・`changes_requested`・`passed`・`failed` 等）を分離して記録する。
  - [例] レビュー Job が `status: "completed"` かつ `result: "changes_requested"`、テスト実行 Job が `status: "completed"` かつ `result: "failed"` であることはいずれも有効な状態。
  - [必須] 依頼を送信しただけ、または `Run` が終了しただけでは Job を `completed` にせず、確認可能な証拠に基づき `criteria` を満たした時点で完了とする。
  - [必須] 結果（`changes_requested`・`failed` 等）に応じて修正や再実行が必要な場合は、完了済み Job を巻き戻さず新しい Ticket を作成する。
  - [定義] 異常終了や中断時は `result` に `interrupted`・`error` 等の結果を残し、継続不能なら理由を記録して Ticket を `canceled` とする。
- [定義] **再開条件と正本保存**：`resume` は Task・Ticket・Job において「何を確認できれば再開できるか」を示す。
  - [必須] 再開・再試行・障害解除・停止判断に不可欠な条件および証拠は、必ず永続的な正本（`depends`・`Run.wait`・`Run.result`・`Ticket.cancel_reason`・対象レコードの `resume`・管理履歴）に保存する。
  - [任意] `depends`・`Run.wait`・管理履歴といった永続正本から再開条件が一意に分かる場合だけ `resume` を省略できる。
  - [禁止] 揮発性 `Handoff` に記載したことを理由に、正本側の `resume` や障害解除条件・再試行条件を省略する。
  - [禁止] 既に正本へ記録された条件を複数箇所へ不要に転記させる。
  - [必須] 中断・引き継ぎ前および重要な発見・失敗時には正本（`Run`・`resume`・管理履歴）と必要な `Handoff` を更新し、再開時は正本および実状態と照合して、条件が変わっていない失敗を根拠なく繰り返さない。
- [定義] **着手判定**：実際の開始記録で判断する。
  - [必須] 親には配下の開始履歴も含める。
  - [禁止] 作成・割り当て・計画だけを開始とみなす。
  - [禁止] 開始履歴を消す、または着手済み作業を `todo` に戻す。

### 5.1. 通常の許可経路

- [任意] `todo`：事前の判断や開始に従う。
  - [任意] 遷移先：`doing`・`waiting`・`paused`・`blocked`・`canceled`。
- [任意] `doing`：着手後の判断や結果に従う。
  - [任意] 遷移先：`waiting`・`paused`・`blocked`・`completed`・`canceled`。
- [任意] `waiting`：待機結果や新たな判断に従う。
  - [任意] 遷移先：`todo`・`doing`・`paused`・`blocked`・`completed`・`canceled`。
- [任意] `paused`：明示解除または中止の判断に従う。
  - [任意] 遷移先：`todo`・`doing`・`waiting`・`blocked`・`canceled`。
- [任意] `blocked`：課題解消・保留・中止の判断に従う。
  - [任意] 遷移先：`todo`・`doing`・`waiting`・`paused`・`canceled`。
- [禁止] `completed`・`canceled`：他の状態へ遷移しない（終端 Ticket・終端 Job・終端 Task の再開禁止）。
- [定義] **Ticket の集約**：自身がキャンセル済みでなければ、全 Job 終端時に `completed` へ集約する。
  - [必須] 第6節の集約を通常経路より優先し、Job の終端確定と同時に反映する。
  - [定義] Ticket に限り、未着手・保留中・ブロック中からも全 Job 終端による完了が成立する。

### 5.2. ガードと操作種別ごとの認可

- [必須] **遷移の検証**：通常経路または Ticket の集約規則、親子規則、および操作種別に応じた認可条件を満たす。拒否時は正本を一切変更しない。
  - [禁止] 定義外の状態・遷移、および対象 Ticket の担当外 Session や閉じた `Run.id` からの状態遷移。
  - [定義] 同じ状態での説明・履歴更新は状態遷移に含めない。
- [必須] **実行操作の認可**：
  - [必須] **Run 開始操作**：実行 Session が対象 Ticket の `worker_id`（`wkr-*`）および `session_id`（`ssn-*`）と一致する適格 Session であり、対象現在 Job、開始状態ガード（対象 Ticket/Job が `todo` または `doing`、前提 `depends` 全 `completed`、親 Task が `paused`・終端でない）、および同一 Ticket で他に未終了の有効な `Run` が存在しないことを検証して新しい `Run`（`run-*`）を開始する。
  - [必須] **Run の実行更新・結果確定操作**：対象 Ticket の `worker_id`・`session_id` と一致する Session であり、対象現在 Job で現在稼働中の有効な `Run.id` であることを照合する。閉じた旧 `Run.id` や別 Session からの更新は拒否する。
- [必須] **管理・評価・証拠取り込み操作の認可**：すべての経路で認可主体の検証・終端状態（`completed`/`canceled`）の復活禁止・監査記録（操作主体・時刻・理由・対象・変更前後）を必須適用する。
  - [必須] **管理操作**：単一 Owner（または権限を持つ運用主体）による Task・Ticket・Job の明示保留（`paused`）・明示解除・中止（`canceled`）・障害解消確認後の `blocked` 復帰・依存変更・範囲変更。
  - [必須] **Task 計画内待機操作（Run を持たない Task）**：単一 Owner（または権限を持つ運用主体）が、Run を持たない Task を外部承認・計画イベント待ちとして `waiting` に遷移させる（解除条件を正本 `Task.resume` または管理履歴へ必須保存）。承認・イベントの確認可能な証拠が到着した際は、証拠を照合して `waiting` を解除し、未着手なら `todo`・着手済みなら `doing`、Task 完了条件（Ticket が1件以上すべて終端し全 `criteria` 成立）を満たしていれば `completed` へ原子的に確定する。
  - [必須] **依存評価操作**：`depends` に基づく未着手 Ticket の `todo ↔ waiting` および前提 Ticket 中止に伴う `blocked` 遷移。前提 Ticket の確定状態に基づいて決定的に評価する（依存解除の `waiting → todo` のみを行い、Run を自動開始しない）。
  - [必須] **証拠取り込み操作**：Run 終了後に到着した確認可能な外部応答・証拠の取り込み。対象 Ticket が `paused`・`blocked`・終端でなく、現在 Job が `waiting` または `doing` である場合に、担当 Session または検証済み証拠を取り込む認可済み主体が、現在 Job の `criteria`・待機条件を照合して `completed`（`result` 確定）または待機解除（`waiting → doing` / `todo`）を原子的に確定する。閉じた旧 `Run.id` 名義からの直接更新は拒否する。
- [必須] `todo`：制約が解消し、対象と配下が未着手。
- [必須] `doing`：開始可能で、待機・保留・障害が解消している。
  - [必須] `todo` からは開始記録を同時確定し、他の状態からは開始履歴がある。
  - [必須] `waiting` 解除後は現在の未完了 Job のみから一方向に続行する。
- [必須] `waiting`：計画内の待機があり、明示保留と継続不能な課題がない。
- [必須] `paused`：明示的な判断があり、未解消の待機・課題を保持する。
- [必須] `blocked`：継続不能な課題があり、保留中なら先に明示解除している。
- [必須] `completed`：第6節の単位ごとの完了判定を満たす。
  - [必須] Task・Job では待機・保留・障害を解消済みである。
  - [必須] Task・Job の `waiting` からは、待機結果の確認可能な証拠によって `criteria`（Task では全 Ticket 終端等の完了条件も含む）が成立する。
- [必須] `canceled`：中止判断・中止理由の記録と、対象範囲の未終了 Run の閉鎖・停止要求を確定する。
- [必須] **復帰先と保留解除の順序**：`paused` 解除前は実行を再開しない。明示解除時は保持していた未解消の障害（`blocked`）・待機（`waiting`）および前提依存を先に再評価し、残存する制約に従う（残る障害があれば `blocked`、残る待機があれば `waiting`）。すべての制約が解消した場合のみ、未着手なら `todo`、着手済みなら `doing` を選ぶ。
  - [禁止] 保留前の状態を無条件に復元する。
  - [禁止] Task・Job の `paused → completed`・`blocked → completed`。

## 6. 親子の整合性と終了判定

- [必須] **一括更新**：関連する状態・開始履歴・実行情報を原子的に確定する。
  - [必須] 最初の実作業開始時は Job・Ticket・`todo` の Task を同時に `doing` にする。
  - [必須] Task が `waiting`・`blocked` なら状態を維持し、開始履歴を追加する。
  - [定義] 親子の状態は同じでなくてよい。
- [定義] **現在 Job**：`jobs` の先頭から見て最初の非終端 Job。
  - [必須] 全先行 Job が `completed` または `canceled` になるまで開始・再試行・完了しない。
  - [必須] 切り替え時は現在 Job と Ticket に残る制約を評価する。
  - [禁止] 後続 Job の事前情報だけで現在の Ticket 状態を変える。
  - [禁止] 完了済み Job への巻き戻しや再入力を行う。
- [必須] **待機・障害の連動**：現在 Job の待機・障害を Ticket にも反映する。
  - [必須] 待機では Ticket の保留・障害・終端を、障害では保留・終端を優先する。
  - [必須] 保留中の待機・課題を保持し、解除時に再評価する。
  - [必須] Job が終端になったら、次の Job または Ticket の終了を判定する。
- [必須] **実行制限**：対象 Ticket または現在 Job の保留（`paused`）・障害（`blocked`）・終端（`completed`/`canceled`）中、および未解除の待機（`waiting`）中は、新しい作業（新規 Job や未解除待機中の次工程）を開始しない。
  - [必須] `waiting` 中の継続・再開では、待機条件（`Run.wait`）と再開位置を評価し、待機解除で `doing` へ遷移した後に同一未完了 Job の残処理を実行する（待機条件の成立により直接 `completed` へ遷移する場合は新 Run 開始を要しない）。
  - [禁止] 親 Task の保留（`paused`）・終端（`completed`/`canceled`）中の開始。
  - [禁止] 親 Task が別 Ticket 起因で `waiting`・`blocked` であることだけを理由に、独立した実行可能 Ticket・Job の開始を停止・拒否する。
  - [必須] 明示保留（`paused`）では、既存実行の安全な停止・中断を求める。
- [必須] **Job 完了**：確認可能な証拠に基づき Job の `criteria` をすべて満たした時点で `completed` とし、`result` および必要な成果物参照を残す。
- [任意] **Job の中止**：必要な Job だけを理由を残して `canceled` にし、後続を続ける。
  - [必須] **中止確定と同時の Run 閉鎖**：該当 Job で実行中の Run がある場合、Job の `canceled` 確定と同時に当該 `Run.id` を終了（`result: "canceled"` 等を記録して閉鎖）し、停止要求を発行する。
  - [必須] **後続 Job 開始前の停止・安全確認**：後続 Job を開始する前に、前の Job の実行が停止（または副作用重複・残存副作用がない安全条件）していることを確認する（残存副作用の疑いがある場合は安全確認完了まで後続 Job 開始を保留する）。
  - [禁止] 中止した Job が目標を達成したとみなす。
- [必須] **Ticket 完了**：全 Job が `completed` または `canceled` になれば `completed` にする。
  - [必須] 自身がすでに `canceled` なら、その状態を維持する。
  - [禁止] Ticket 独自の完了条件や承認項目を追加する。
  - [定義] 全 Job が中止でも処理終了を表し、目標達成を保証しない。
  - [必須] Ticket 終了時に正式な成果・結果・状態を永続化する。
  - [定義] 次 Ticket が作成されていなくても、終了済み Ticket をアーカイブ・折りたたみできる。
- [必須] **Task 完了**：Task の `criteria` を満たし、未解決の必須成果物がない。
  - [必須] Ticket が1件以上あり、すべて終端状態。
  - [必須] 中止 Job・中止 Ticket や差し戻し結果で未達となった必須範囲を解決するか、単一 Owner（または権限を持つ主体）が理由付きで除外する。
  - [必須] Task 完了時に Task 所属の揮発性 `Handoff` を消去し、恒久的に再利用する知見のみを `Project.knowledge` へ昇格させる。
  - [禁止] Ticket の処理終了や完了 Ticket 数だけを目標達成の証拠にする。
- [必須] **Task・Ticket の中止**：未終端の子孫を同時に `canceled` にし、Ticket では中止理由（`cancel_reason`）を必須記録する。
  - [必須] 終端済みの子を保持し、実行中の Run があれば閉鎖して停止を要求する。
  - [必須] 明示的な中止を、全 Job 終端による Ticket 完了より優先する。
  - [禁止] 遅延結果で終端状態を復活させる、または停止要求だけで終了確認にする。
- [必須] **終端の保持**：保存中の状態・成果・中止理由・履歴を改ざんしない。
  - [禁止] プロセスの正常終了だけで作業を完了する。
  - [必須] 追加・訂正・修正・再実行は新 Ticket にし、親 Task も終端なら別の非終端 Task を使う。
  - [定義] 終了後の保存・削除方法と保持期限は規格の対象外。

## 7. 実行依存と情報共有参照

- [任意] **実行依存**：`depends` に、先に処理を終える必要がある前提 Ticket の ID を記録する。
  - [定義] 複数指定はすべての処理完了を待ち、空の一覧は前提なしを意味する。
  - [任意] 別 Task・別 Project の Ticket を参照する。
  - [必須] 参照先または検証可能な完了記録の存在を確認する。
  - [禁止] 自己依存・重複参照・循環する完了依存。
- [必須] **完了依存グラフの辺と循環禁止**：
  - [定義] 完了依存グラフの有向辺に含めるのは、(1) 非終端 Ticket の `depends` による前提 Ticket への辺、および (2) 表示上の状態（`waiting`・`paused`・`blocked` 等）によらず、非終端 Ticket・Job が保持しているすべての未解決待機における `Run.wait` の別 Ticket 完了待ちへの辺とする。
  - [必須] 解消済み・解除済みとなった `Run.wait` は実行履歴として保持しつつ完了依存グラフの辺から除外する（待機が解消・解除された後に逆向きの完了依存を登録することは循環に該当せず許可される）。
  - [必須] 完了依存の登録・変更（静的 `depends` と動的 `Run.wait` の混在を含む）は、循環を閉じ得る逆向き登録が並行に発行されても双方同時に成功しない原子的な循環検証で評価する。
- [必須] **実行依存の評価**：全依存先が `completed` になった場合だけ開始する。
  - [必須] 前提待ちは `waiting` とし、保留・障害・終端を優先する。未着手 Ticket は依存評価経路で `waiting → todo`（前提中止で継続不能なら `waiting → blocked`）へ再評価・遷移できる。
  - [禁止] Ticket 自身のキャンセル・削除・不明状態を完了とみなす。
  - [必須] 前提 Ticket のキャンセルで継続不能なら、保留中・終端を除いて `blocked` とする。
  - [定義] 完了 Ticket に中止 Job が含まれることは許容される。
  - [必須] 必要な入力や成果の有無は、作業内容と結果から確認する。
- [任意] **実行依存の変更**：未着手の Ticket に限り、理由と変更前後を残して修正する。
  - [必須] 参照・循環・現在の制約を再評価する。
  - [禁止] 着手後・終端後の変更、固定 Job の意味を変える修正。
- [任意] **情報共有参照**：`refs` に、重複作業や文脈断絶を避けるための関連 Ticket 参照を記録する。
  - [例] 前 Ticket の成果物・完了結果・中止理由の参照、派生元 Ticket、修正対象 Ticket、再実行元 Ticket。
  - [必須] `refs` は情報共有専用とし、実行依存 `depends` と明確に区別する。
  - [禁止] `refs` を開始条件・完了待機・状態遷移の制約として解釈する。
  - [任意] 参照要素には `ticket_id` と任意の補足ラベル（`kind`：`derived_from`・`fixes`・`rerun_of`・`related` 等）や短文メモ（`note`）を記載する。
  - [禁止] `refs` の `kind` によって業務ロジックや状態遷移を分岐させる。
- [定義] **課題対応・修正・再実行**：ブロックされた課題の解消、差し戻しへの修正、異常終了や Session 再開不可からの再実行はいずれも通常の新 Ticket で行う。
  - [必須] 元 Ticket が継続不能な場合は、`cancel_reason` を記録して `canceled` とし、新 Ticket の `refs` で元 Ticket を参照する。
  - [必須] 元 Ticket が継続可能で一時的に `blocked` となった場合は、元 Ticket の正本（`resume`・管理履歴）に障害内容と解除条件を記録し、修復用新 Ticket の `refs` に元 Ticket を記録して、元 Ticket 側で実際の課題解消を確認してから再開する。
  - [推奨] 修復用 Ticket を、元 Ticket の処理完了待ち（`depends`）にしない。
  - [禁止] 別 Ticket の完了だけを理由に元 Ticket の障害を自動解除する。

## 8. Run・再試行と再開不可時の引き継ぎ

### 8.1. Run（実行試行の正本）

- [定義] **Run**：Job の1回の実行試行（Execution / Attempt に相当）を記録する正本。
  - [必須] `Run` は `Job` にかかる実行試行であるため、`Job` の外に出さず、各 `Job` オブジェクトの内部フィールド `runs`（`tickets[].jobs[].runs[]`：未実行等の空配列時は `[]` または記載省略）として保持する。
  - [必須] `id`（接頭辞 `run-`）と `started`（実作業開始時刻 ISO 8601）を必須記録する。
  - [必須] Run は実行中であれば `result`（および `ended`）がまだ無く、終了確定時に `result`（`succeeded`・`failed`・`canceled`・`interrupted`・`error` 等）を必須記録し、終了時刻を確認できる場合は `ended` も記録する。
  - [禁止] `Run` 内に外出し用の逆参照（`ticket_id`・`job`・`worker_id`・`session_id` および `Run.wait.job_id`）を重複記載する。
  - [必須] 同一 Ticket で同時に稼働する有効な実行試行（`Run`）は最大1つとする。
  - [必須] 正常終了・異常終了・Job 単独中止・Ticket 中止により Run が終了確定した時点でその `Run.id` を即座に閉じ、閉じた `Run.id` からの後着結果・業務状態更新・Handoff 更新を拒否する。
  - [定義] 独立した `Execution` や `Attempt` オブジェクトを別途設けず、`Run` を実行試行の正本として統一する。
  - [必須] すべての作業主体による実行を同じ `Run` 形式で記録する。
- [必須] **待機・実行制御情報**：待機中の制御情報（待機対象の参照 `target`、解除条件 `condition`、待機開始時刻 `since`、再開位置 `resume_point`、タイムアウト `timeout`、および解消・解除時の `resolved` 時刻）は Job 直下に複雑構造として追加せず、各 Job 内の `Run.wait` で保持する。
  - [必須] `waiting` 解除後は現在の未完了 Job のみから一方向に続行し、閉じた旧 `Run.id` からの状態更新を拒否する。
  - [必須] 別 Ticket の結果を待つ場合も、第7節の完了依存グラフ（`depends` と非終端の未解決 `Run.wait`）に循環が存在しないことを保証する。
- [定義] **複合スクリプトと副作用管理**：複合スクリプトは Ticket 単位で管理する。
  - [定義] 細かな内部関数やコマンドすべてを個別の Job として定義する必要はないが、各 Job の完了判定には確認可能な証拠が必要。
  - [必須] 複合スクリプト内の外部操作待ちも通常の `waiting` で扱い、待機対象の Worker 種別は問わない。
  - [任意] 独立作業が必要なら別 Worker を担当とする別 Ticket を生成し、単純な操作結果の通知で完結するなら必ずしも別 Ticket を作らない。
  - [必須] 異常終了や Session 再開不可で継続不能となった場合は `cancel_reason` を記録して Ticket を `canceled` とし、元 Ticket は再開せず、修正・再実行は新 Ticket で管理する。
  - [必須] 障害注入等の副作用を持つスクリプトでは、Ticket の中止と環境復旧を分離し、実行停止時または中断前に開始済みの外部操作がある場合に副作用が残存している可能性があるなら、安全確認・環境復旧の完了まで後続の危険な実行を禁止・保留する。

### 8.2. 同一 Ticket・同一 Session 内での Job 再試行

- [必須] **回復可能な中断と再試行**：同一 Ticket・同一 Session 内で一時的なエラーやタイムアウトにより 1 回目の `Run` が `result: "failed"` 等で終了したものの、同じ作業計画のまま回復可能である場合は、計画の破綻と区別する。
  - [必須] 元の Ticket・Job の `status` が `doing` ならその状態を維持し、失敗した旧 `Run` に `result: "failed"`（および確認できれば `ended`）を記録して閉じる。
  - [必須] 前の実行が停止（または残存副作用がない安全条件）していることを確認した上で、同一 Ticket・同一 Session で当該 Job の `runs` 配列に新しい `Run`（`run-*`）を追加して再試行する。
  - [禁止] Run の 1 回の終了・失敗だけで即座に Job や Ticket の完了・中止・ブロックを判断する。
  - [禁止] 計画された再試行・タイムアウト処理が残る間、時間超過だけで `blocked` にする。
  - [禁止] 監視の再接続や同一操作の再送だけで、別の `Run` として二重登録する。
- [任意] **並列実行と優先度**：資源競合を制御しつつ、独立した別 Ticket を並列実行する。
  - [禁止] 同一 Task に属することや Handoff が単一スロットであることを理由に、無関係な Ticket の並列実行を遮る・直列化する。
  - [任意] `priority` を開始順の判断材料にする。
  - [禁止] 低い優先度だけで `paused` にする。

### 8.3. Worker / Session 再開不可時の旧 Ticket 中止と新規 Ticket 起票

- [必須] **担当セッション不変の原則**：1つの Ticket の担当（`worker_id`・`session_id`）は途中で変わらない。担当 Worker または担当 Session が無応答・再開不可となった場合は、既存 Ticket の `worker_id` や `session_id` を付け替えるのではなく、旧 Ticket を閉じて新規 Ticket を起票し、新しい Session で稼働させる。
- [必須] **新規 Ticket 引き継ぎの可否条件**：
  - [禁止] 前の実行が稼働中または停止未確認の状態で旧 Ticket を強制引き継ぎする（Handoff の閲覧は可）。
  - [必須] 前の実行が停止（または残存副作用がない安全条件）していることを確認できた場合のみ、旧 Ticket を中止して新規 Ticket へ引き継ぐ（停止前に開始された外部操作や副作用の残存が疑われる場合は安全確認・復旧完了まで保留）。
- [必須] **旧 Ticket の閉鎖と新規 Ticket の作成手順**：
  1. 前の実行が停止（または残存副作用がない安全条件）していることを確認した上で、旧 Run を終了（`result: "canceled"` または `"interrupted"` 等、確認できれば `ended` を記録）して閉鎖する。
  2. 旧 Ticket（および未完了の Job）を中止理由（`cancel_reason`）付きで `status: "canceled"` として終端化・閉鎖する（旧 Ticket の `worker_id`・`session_id` および完了済み Job の成果はそのまま保持する）。
  3. 同一 Task 配下に、新しい担当セッション（別 Worker の `wkr-*` / `ssn-*`、または同一 Worker の新しい `ssn-*`）を持つ新規 Ticket（`tkt-*`）を起票し、`refs`（`kind: "derived_from"` や `"rerun_of"` 等）で旧 Ticket を参照し、必要に応じて Task の揮発性 `Handoff` で作業文脈を引き継いで新 Session で `Run` を開始する。

## 9. Handoff と長期知識

### 9.1. Task 所属の揮発性 Handoff

- [定義] **Handoff**：`Task` オブジェクトの内部フィールド `handoff`（`project.tasks[].handoff`：`Handoff | null`、任意・未設定時は省略可）として保持する揮発性の単一スロット（Task ごとに最大1つ）。
  - [必須] `Task` の内側に配置されるため逆参照の `Handoff.task_id` は持たず、内部キーとして状況に応じて `current_ticket_id`（`tkt-*`）・`worker_id`（`wkr-*`）・`session_id`（`ssn-*`）・`current_job_id`（`job-*`）・`context`・`stop_position`・`blockers`・`notes`・`updated` を保持する（`blockers`・`notes` は空配列時は省略可）。
  - [必須] Task への参照権限を持つ複数の Session が同時に閲覧できる。
  - [必須] 閲覧権限と実行権限を厳格に分離し、Handoff を閲覧できることを Ticket の実行権限と同一視しない。
  - [禁止] Handoff 自体にコマンド実行機能や状態遷移を直接引き起こす機能を持たせる。
  - [定義] **揮発性と Task 完了時の消去**：Handoff は正本から得られる現在状況の要約表示と揮発性の補足キャッシュであり、正式な監査履歴・成果物・再開条件の正本としない。Task が完了（`completed`）した時点で揮発性 Handoff は消去し、恒久的に再利用すべき知見のみを `Project.knowledge` へ昇格させる。
  - [必須] Handoff は必要に応じて再生成・破棄でき、Handoff が消失しても Task の状態、Ticket の履歴、Job の達成結果、Ticket の中止理由、Artifact、正本 `resume`、Run 履歴（`wait` 含む）、管理履歴は失われず、正本のみから再開判断と Handoff 再生成を行える。
  - [必須] Task 内の無関係な Ticket の並列実行を Handoff によって遮ったり直列化したりしない。
  - [禁止] 閉じた旧 `Run.id` や権限のない Session から Handoff を上書きする。
  - [必須] Ticket 終了時に正式な成果・結果・状態を永続化し、Handoff を長期記憶として扱わない。

### 9.2. Project の長期知識

- [定義] **長期知識**：Project の `knowledge` に再利用する内容と根拠を保持する。
  - [必須] `content` に残す内容、`basis` に根拠・判断理由・出典をまとめる。
  - [例] 未記載の事実・暗黙のルール・過去の判断・将来の展望。
  - [必須] 元の Task・Ticket がなくても内容と判断経緯を理解できる。
  - [禁止] 未確認の内容や展望を確認済みの事実として扱う。
  - [必須] 再利用する知見は Project の知識へ選別して移し、Handoff の全文を無条件に複製しない。
- [定義] **知識の状態**：現在使う知識と、過去の知識を2つの値で区別する（v1.0.0 の綴りを維持）。
  - [定義] `active`：現在の知識として採用している内容。
  - [定義] `supersed`：置換・廃止等により現在は使わない内容。
  - [必須] 新規記録は未指定でも `active` とする。
  - [例] 「次回は配信を自動化する予定」という計画も `active` の知識。
  - [必須] 状態の変更主体・時刻・理由を履歴に残す。
  - [必須] 通常は `active`、振り返り・再発障害・判断理由の確認では `supersed` も参照する。
- [必須] **知識の履歴**：内容や根拠の訂正は新しい記録にして元を残す。
  - [必須] 置換時は `supersedes` で同じ Project の現在の知識を参照する。
  - [必須] 旧記録の `supersed` と新記録の `active` を同時確定する。
  - [任意] 後継がない場合も、理由を残して `active` から `supersed` にする。
  - [任意] 同じ内容を再び使う場合は、理由を残して `supersed` から `active` に戻す。
  - [禁止] 内容・根拠の上書き、自己参照、循環。

## 10. 禁止事項・記録・適合確認

### 10.1. 禁止事項（不変条件）

- [禁止] 1. 人間、Bot、AI 等を異なる業務上の作業主体として扱う。
- [禁止] 2. `owner_type` を必須にする。
- [禁止] 3. Worker の種類で Job の状態遷移を分岐する。
- [禁止] 4. `Request` を独立した業務オブジェクトにする。
- [禁止] 5. Job に複雑なワークフロー構造を追加する。
- [禁止] 6. Job に個別担当を設定する。
- [禁止] 7. Ticket に複数担当を設定する、または途中で Ticket の担当（`worker_id`・`session_id`）を変更する。
- [禁止] 8. Ticket 確定後に Job 列を変更する。
- [禁止] 9. 終了済み Ticket を再開する。
- [禁止] 10. 循環する完了依存を許す。
- [禁止] 11. Handoff の閲覧権限を実行権と同一視する。
- [禁止] 12. Worker が同じという理由で別 Session に無断実行させる。
- [禁止] 13. 稼働中の Session から作業を強制引き継ぎする。
- [禁止] 14. 前の実行の停止（または残存副作用がない安全条件）を確認せずに作業を引き継ぐ。
- [禁止] 15. Handoff を正式履歴の正本にする、または Task 完了後も恒久 Handoff として残す。
- [禁止] 16. Handoff によって無関係な Ticket を直列化する。
- [禁止] 17. 特定の Agent・Bot・オーケストレーターへの依存を TTJ へ組み込む。

### 10.2. 記録と適合確認

- [任意] **保存形式**：意味と参照を保てれば、保存先・データ構造・UI 等を選べる。
  - [禁止] 特定の保存期間や自動削除を規格として強制する。
- [必須] **管理記録**：作成・状態変更・開始・結果・中止・異常停止・再試行・再開不可時の旧 Ticket 中止と新規 Ticket 起票・依存変更・範囲変更・期限変更・知識の採用・管理/評価/証拠取り込み操作を追跡する。
  - [必須] 変更前後・主体（`worker_id`・`session_id`、または管理主体）・時刻・理由と関連する実行（`run`）を識別する。
  - [任意] 時刻等は更新手段が補完する。
  - [禁止] 補完できない事実を捏造する。
- [必須] **整合性**：現在状態・現行 Run・管理情報・履歴を原子的に確定する。
  - [禁止] 同じ操作の再送で状態変更や副作用を二重確定する。
  - [禁止] 閉じた旧 `Run.id` や対象外 Session から業務状態を更新する。
  - [任意] 無効な結果を状態へ反映せず監査記録に残す。
- [必須] **確認結果**：成果と検証を一度記録し、親では参照する。
  - [禁止] 記録で分かる結果や管理情報を各階層へ転記させる。
- [必須] **準拠**：本書のすべての [必須] と [禁止] を満たす。
  - [必須] 部分適用では未対応範囲を示す。
  - [禁止] JSON や Skill だけで永続化・原子性・排他・外部副作用防止を保証したと称する。
- [必須] **適合確認**：7種の自動採番 ID 形式（`<接頭辞>-<英数字6桁または8桁>-<ゼロ埋めなしインクリメント>`：接頭辞 `pj-`・`tsk-`・`tkt-`・`job-`・`run-`・`wkr-`・`ssn-`）・配列と単一オブジェクトの原則に基づく `project.tasks[]`（`project` は単一オブジェクト）とルート `tickets[].jobs[].runs[]`（`Ticket.task_id` 必須）の分離スキーマと省略規則およびファイル分割対応（`Task` 内の `tickets` 保持・逆参照 `Task.project`・`Handoff.task_id` および `Ticket.jobs` の ID 配列分離の廃止）・単一 Owner 原則・Ticket の `worker_id` および `session_id` 固定・Job の `status`/`result` 分離・依存循環拒否（保留/一時障害で保持中の未解決待機辺含む）・同一 Ticket/Session 内の新 Run 再試行・再開不可時の旧 Ticket 中止と `refs` 付き新規 Ticket 起票・揮発性 Handoff の Task 完了時消去と長期知識への昇格・保留解除時の再評価・Worker 非依存性を合わせて検証する。
  - [必須] 全 Job 終端時の Ticket 完了と、Ticket 自身の中止優先を確認する。
  - [必須] 中止 Job を含む Ticket の処理終了や Ticket 完了数と、Task の目標達成を区別する。
  - [必須] 同一 Worker の別 Session 無断実行、閉じた旧 Run 結果からの更新、前の実行が稼働中・停止未確認時の引き継ぎを拒否する。
  - [必須] Handoff 消失および再起動後も Task・Ticket・Job・中止理由・Artifact・正本 `resume`・Run の正式履歴から再開判断できることを確認する。
  - [必須] 独立した Ticket の並列実行と、次 Ticket 未作成での終了 Ticket アーカイブ・折りたたみが妨げられないことを確認する。
  - [必須] 短期の揮発性 Handoff と、採用中（`active`）および過去（`supersed`）の長期知識を区別して参照できる。
